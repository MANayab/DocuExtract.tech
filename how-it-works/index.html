How DocuExtract turns invoice PDFs into structured data

DocuExtract processes batches of up to 50 PDFs locally, extracts text, optionally runs local English OCR when bundled, applies heuristic extraction and validation, then presents results for review before export.

What happens when you select a PDF?

The processing workflow starts when you select a document in the live application. Application code processes the file locally in the browser instead of uploading the invoice to an application backend. Each PDF is limited to 25 MB and 100 pages. OCR, when included in a build, is limited to English and 20 pages per PDF.

A PDF may contain selectable text or scanned page images. Optional Tesseract OCR can read English scans locally only when the build includes OCR assets. It is limited to 20 pages, capped at 75% confidence, always marked Review, and may struggle with poor scans, handwriting or skewed pages. The currently deployed app's OCR assets are NOT VERIFIED.

  1. Select the document. Choose up to 50 PDFs (25 MB and 100 pages maximum per file). A PDF may contain multiple invoices.
  2. Read and interpret text. The extraction logic uses document text and heuristic rules to identify fields and line items.
  3. Validate the structure. Extracted data is validated using Zod.
  4. Review the result. Check the fields and correct mistakes before export.
  5. Export the reviewed data. Choose the format suited to the next task.

How are invoice fields and line items detected?

Extraction is heuristic: the application applies rules to the text and layout information available from a PDF. It is not a guarantee that every vendor template, field label, or table arrangement will be interpreted correctly.

Labels and values must be on the same line or in neighbouring columns of the same row. A layout that places a label above its value is not read by the documented extraction approach. This is an important compatibility boundary when deciding which PDFs to process.

Line items are detected using column gaps and the table header. Unusual column spacing, multi-line descriptions, or atypical tables can lead to rows or values that need correction. Use the review screen to compare extracted rows with the source invoice rather than assuming that a plausible-looking spreadsheet is correct.

The locale selector supports en-IN, en-US, en-GB and de-DE for date and number parsing. Ambiguous dates are flagged; reprocessing protects manual edits. Review the date against the original document, especially when the source convention could be ambiguous.

GST-aware fields and locale parsing

Supported fields include GSTIN, HSN, taxable value, tax rate, tax amount and CGST, SGST and IGST. These are heuristic candidates, not guaranteed results; verify tax details against the source invoice.

Select en-IN, en-US, en-GB or de-DE to interpret date and number formats. Ambiguous numeric dates are flagged. Reprocessing with another locale protects manual edits, but all changed values still require review.

Batch processing and status

Drop up to 50 PDFs. Files are processed one at a time with per-file progress, status indicators and possible-duplicate warnings. Each file is limited to 25 MB and 100 pages; OCR is limited to 20 pages.

Which export format should you choose?

DocuExtract provides a combined XLSX workbook, invoice-level CSV, line-item CSV, and JSON with validation status.

XLSX

Choose XLSX when you want a spreadsheet file containing the full invoice data. Review the extracted fields and line-item rows before using the workbook in an accounting or reporting workflow.

CSV

Choose invoice-level CSV for invoice summary rows or line-item CSV for item rows. CSV scope depends on the export selected. do not use it as a complete substitute for XLSX or JSON when header-level invoice fields are required.

JSON

Choose JSON when structured invoice data is the desired output. JSON is useful for inspecting data structures or passing reviewed records into a subsequent process. Validate any downstream assumptions independently.

Exports apply formula-injection sanitization. This is a defensive measure for exported values that could otherwise be interpreted as spreadsheet formulas. It does not make inaccurate extraction accurate or replace reviewing the document.

How does the browser-processing privacy design work?

DocuExtract has no application backend, account, database, analytics or telemetry. Application code does not upload selected invoice files to a server. Users can inspect their browser's network tab to independently verify the network activity observed while processing a document.

Invoice data is never written to URLs, localStorage or sessionStorage. PDF buffers are released and documents are destroyed after processing. React rendering does not use dangerouslySetInnerHTML.

These details describe the application's documented design, not a blanket guarantee about every component of a user's device or browsing environment. Browser extensions, device compromise, operating-system access, and the hosting provider's standard server logs are separate considerations. See the privacy page and the repository's PRIVACY.md.

What are the extraction limitations and workarounds?

DocuExtract is a practical extraction aid, not an authoritative accounting record generator. Its current boundaries should inform how you prepare documents and review results.

  • Labels above values: these layouts are not read. Use a compatible invoice layout where labels and values share a line or row, or manually correct the output if the review workflow permits it.
  • Ambiguous numeric dates: the app reads dates such as 05/09/2026 as DD/MM/YYYY and flags them. Confirm the date using the original invoice.
  • Unusual line-item tables: column-gap and header detection may need manual correction. Compare each quantity, description and amount with the source.
  • Scanned documents: OCR is optional and build-dependent. When bundled, it supports English only up to 20 pages, is capped at 75% confidence and always needs review.
  • Encrypted files: encrypted PDFs are rejected unless already decrypted. Provide an accessible, decrypted document where you are authorized to do so.
  • Corrupt files: the app does not support corrupt PDFs. Obtain a valid copy from the document issuer.
  • Handwriting: recognition is not guaranteed. Check all handwritten fields manually and do not rely on an unverified extraction.
  • Several invoices in one file: splitting relies on invoice-number changes. Multi-page invoices are kept together, but boundary edge cases are not fully tested; inspect the split results.
  • CSV scope: choose invoice-level CSV or line-item CSV. XLSX combines invoice rows and supporting sheets; JSON includes validation status.

Every output must be reviewed before accounting, tax, payment or legal use. Compare important fields and totals with the original document and follow your organization's approval procedures.

Which technologies support the tool?

The application uses React 18, TypeScript, Vite, Tailwind CSS, pdf.js, ExcelJS and Zod. Tests use Vitest, Testing Library and Playwright, and deployment uses GitHub Actions.

The source is available in the DocuExtract repository. For bug reports and questions about observed behavior, use the GitHub issue tracker.
